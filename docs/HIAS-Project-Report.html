1. Abstract

Allocating invigilators to examination halls is a recurring, manual task in every college. Done by hand, it is slow and error-prone: the same person can be sent to the same hall repeatedly while others are not, a hall can be double-booked, and there is no record to check fairness against afterwards.

HIAS (Hall Invigilator Allocation System) is a Windows desktop application that automates this task. For every exam session it assigns each on-duty staff member to a hall using a rotation algorithm that remembers each person's previous halls, validates the result against seven rules, allows controlled manual edits with an audit trail, and produces printable PDF allocation sheets and reports. It runs completely offline with an embedded SQLite database, so it can be installed on any college computer without a server or internet connection.

2. Problem statement and objectives

Problem

  • Manual allocation for each session takes significant time for the examination cell.
  • Fair rotation is hard to guarantee by memory or spreadsheets: staff may repeat halls before others have had a turn.
  • Mistakes such as one hall assigned to two people, or one person to two halls, are easy to make and are found late.
  • There is no reliable history to answer "Who was in hall H104 on 3 November?" or to justify an allocation.

Objectives

  1. Generate a complete, fair hall allocation for a session in one click.
  2. Rotate halls across sessions and exam series so nobody repeats a hall before completing the rotation.
  3. Validate every allocation automatically before it is finalised.
  4. Allow justified manual changes while keeping a record of what was changed and why.
  5. Produce printable, college-branded reports.
  6. Work offline on an ordinary Windows computer with simple installation and backup.

Offline and safe
No internet or server needed; one-click backup and restore; destructive actions require typed confirmation.

4. System architecture

HIAS is an Electron application with three layers. The user interface never touches the database directly; every operation goes through a narrow, typed IPC bridge to the main process, which owns the business logic and the database file.

  • Security: the UI runs with contextIsolation on and Node integration off; it can only call the functions the preload bridge exposes.
  • Data safety: multi-step operations (confirming an allocation, deleting a batch) run inside database transactions, and the database file is written to disk after every committed change.
  • Offline: fonts and all assets are bundled; the packaged app makes no network requests (verified during testing).
  • Web build: the same UI can also be built as a browser application (npm run build:web) that stores data in the browser; the desktop application is the supported deployment.

7. Allocation algorithm and validation rules

Rotation algorithm

  1. The halls selected for a session form an ordered hall pool (ordered by sort order, then id, so the order is always deterministic).
  2. For each selected staff member, HIAS reads their confirmed hall history from rotation_history.
  3. Every (staff, hall) pair gets a cost: a very large penalty if the hall is among the person's last n − 1 halls (rule R1, larger for more recent visits), plus how often they have already had that hall, plus the circular distance from their last hall (so the natural "next hall" is preferred).
  4. All staff of the session are assigned together by finding the minimum-cost perfect matching (the Hungarian algorithm, O(n³)). Because the R1 penalty outweighs everything else, no rule is broken whenever a valid assignment exists, and with a fixed team the result is the classic perfect rotation (everyone moves one hall on).
  5. When the staff on duty vary, a repeat can be mathematically unavoidable (for example, two people whose only remaining hall is the same one). The algorithm then uses the minimum possible number of repeats, choosing the hall visited longest ago.
  6. The result is saved as a draft. Only when the administrator confirms it is it written to rotation_history, inside a transaction, which moves the rotation forward.

Because the rotation history is global rather than per batch, fairness carries over from one exam series to the next. An administrator can reset it deliberately (Restart Rotation), for example at the start of an academic year.

Validation rules

RuleCheck
R1No repeated hall: a staff member may not return to a hall used within their last n − 1 confirmed sessions, where n is the pool size (so a full cycle may restart).
R2A hall has at most one invigilator in a session.
R3A staff member has at most one hall in a session.
R4Rotation integrity: a session follows the last confirmed session in step order.
R5Staff must be active.
R6Halls must be active.
R7The number of staff equals the number of halls.

R1 is enforced strictly with one exception: if an allocation has no more repeats than the proven minimum for the staff and halls of that session, the repeats are shown to the administrator as warnings ("unavoidable repeat") instead of blocking the session. Manual edits are checked against the rules as they are made, and the edit dialog only offers halls that keep the allocation valid.

Why a matching algorithm

An earlier version assigned halls one person at a time. Fairness testing showed that this worked perfectly for a fixed team but failed badly when more staff than halls take turns (the normal case in a college): two people competed for the same "next" hall and one was pushed into a recently used hall, so the system rejected its own allocation. With 10 staff sharing 6 halls, only 5 of 60 sessions could be confirmed; with a random duty list of 6 out of 12 staff, 9 of 80. Assigning everyone together as an optimal matching fixed this: all sessions in every tested scenario now confirm.

8. Testing and quality

Automated tests

72 automated tests (Vitest) run against an in-memory database and all pass. They cover:

  • The rotation algorithm: first allocation, circular wrap-around, staff who join later, pools smaller than the total number of halls, ordering across batches.
  • Every validation rule, including a regression test for a full-cycle restart that an earlier version wrongly blocked.
  • The allocation lifecycle: generate, edit, confirm, delete draft sessions, permanent staff deletion, rotation restart, and batch status updates.
  • A fairness suite of 12 multi-session scenarios run through the real engine, validator and database (below).

Fairness testing

Each scenario generates and confirms every session in turn and checks that no hall or person is double-booked. "Hall spread" is, for the worst-off person, the difference between the hall they had most often and least often.

10. Limitations and future work

Current limitations

  • Single computer. Data lives on the computer where HIAS is installed; several computers cannot share it live. Backup and restore move data between computers.
  • No user accounts in the desktop app. Anyone who can open the app has full access, so it should be installed on a computer used only by the examination cell.
  • Unsigned installer. Windows shows a SmartScreen warning on first install.
  • Hall order is fixed by creation order; there is no screen to reorder halls.

Possible enhancements

  • A shared network database so several computers can work on the same data.
  • Optional administrator password for the desktop app.
  • Excel export of reports, and SMS or e-mail duty notifications to staff.
  • Workload balancing so the number of duties per person evens out across a batch.
  • Hall reordering and seat-capacity-based allocation.

11. Conclusion

HIAS replaces a slow, manual and error-prone process with a reliable tool: an entire session is allocated in one click, fairness is enforced by a rotation that remembers every confirmed duty, mistakes are caught by automatic rule checks before anything is finalised, and every change is recorded. Delivered as an offline Windows application with printable reports, backup and a user guide, it is ready to be used by the examination cell.
